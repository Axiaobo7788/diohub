# DioHub 二次开发实施约束

最后更新：2026-08-14

## 1. 总原则

每一次修改都必须朝完整、统一、可长期维护的产品方向推进。
“代码存在”“能打开”“测试通过一部分”只表示基础能力可用，不等于用户要求已经完成。

实现应与当前阶段范围相称，但不得用临时占位、重复外壳或最低可运行版本替代已经明确要求的完整页面和交互。

产品平台边界是 Android 与 Desktop（Windows、macOS、Linux）共享 Flutter 信息架构和业务实现。现阶段要求
Android 与 Linux 基准并不表示可以破坏 Windows/macOS；未在对应 runner 验证的平台必须明确标记。

## 2. 范围与完成状态

1. 开始前必须按用户原始编号建立验收映射，后续讨论不能静默缩小或替换原始事项。
2. 若只完成数据源、Provider、分页或其他前置能力，只能报告“基础设施完成，页面未完成”。
3. 只有同时满足以下条件，页面事项才可标记为“完成”：
   - 已接入正式路由，用户可以从真实入口到达。
   - 使用真实业务数据，不以演示数据或硬编码计数伪装。
   - 加载、刷新、空数据、错误、重试和分页状态完整。
   - 返回、Tab 切换、深链和登录权限行为明确。
   - 360px、800px、1440px 的信息结构与触控/桌面交互均可用，无布局溢出。
   - 新增客户端文案进入官方 `gen_l10n`；仓库名、README、Issue/PR 标题等用户内容保持原文。
   - 关键路径有 Widget Test，相关分析不新增 error/warning。
4. 不能用“相关测试通过”替代需求验收；测试必须对应用户可见的完成条件。
5. 状态报告必须分别列出：完成、基础设施完成但页面未完成、阻塞、尚未开始。

## 3. UI 与架构一致性

1. Home、Repository 和后续迁移页面必须复用同一个全局 App Chrome；顶栏、全局抽屉、账户菜单、搜索位置和全局导航语义只有一个实现与一套尺寸 token。
2. 页面专属 Theme、密度和导航只能作用于页面内容，不得改变全局 App Chrome。
3. 页面局部侧栏必须明确命名和职责，不能与全局导航抽屉形成看似相同但尺寸、跳转和样式不同的第二套全局导航。
4. Issues 与 Pull requests 共用搜索、分页和基础行结构，但必须保留各自的信息字段、筛选语义、空状态和创建流程，不能只换图标冒充两个页面。
5. 优先复用现有 API、GraphQL、Provider、Controller、缓存、模型和详情路由；不得因 UI 重写建立第二套业务模型或请求链。
6. 未取得的数据必须隐藏、禁用或显示诚实的不可用状态，不得使用推测值或本地占位文字伪装真实数据。
7. 认证状态必须区分“仍在初始化”“已登录”“已确认未登录”；不能把 loading 当作 guest，造成登录提示闪烁或提前发起错误请求。
8. “未登录不请求”“已取消旧请求”等结论必须由生产页面外壳到真实 Provider 边界的测试证明；只测试叶组件没有挂载请求 Widget，不足以证明端到端行为。

## 4. 性能与加载合同

### 4.1 测量原则

1. 流畅度和性能结论只能来自 Profile 或 Release 模式；Debug 只用于功能调试。
2. 项目必须固定至少一台 Android 设备和一套 Linux 基准环境。基线尚未实际建立时必须写“尚未建立基线”，不能填写猜测数字。
3. 每份性能记录至少包含：
   - 设备型号、CPU、内存和屏幕刷新率。
   - 操作系统、Flutter/Dart 版本、Git 提交和构建模式。
   - 网络条件、账号/仓库、冷缓存或暖缓存状态。
   - 可重复的操作路径和样本数。
   - UI/Raster 帧数据、长帧比例以及原始 DevTools/trace 位置。
4. 启动、导航、滚动、Markdown 渲染和长列表必须分别记录，不能用一个笼统数字代表整套应用。
5. 新功能合入前后必须在相同环境、数据和路径上对比；网络耗时与本地 UI/解析耗时必须分开。
6. 不得用硬编码延迟、只等待固定毫秒数的测试或 Debug 观感证明达到性能目标。

### 4.2 帧预算

| 场景 | 工程目标 |
| --- | --- |
| 60Hz 设备 | 单帧预算 16.67ms |
| 120Hz 设备 | 单帧预算 8.33ms |
| 核心滚动与转场 | UI/Raster p95 尽量保持在对应帧预算内 |
| 超预算帧 | 目标低于 2% |
| 严重长帧 | 核心路径不得出现可稳定复现的 50ms 以上长帧 |
| 性能回归 | 相同环境下不得无说明地回退超过 10% |

受设备、网络或第三方内容影响无法达到目标时，必须保留测量证据并解释原因，不能直接删除或放宽约束。

### 4.3 交互与加载时序

以下数字是基准环境下的工程目标，不是通过硬编码延迟实现的测试条件：

- 用户操作后 100ms 内出现视觉反馈。
- 稳定页面外壳、缓存内容或同构骨架目标在 150ms 内出现。
- 暖缓存时主要内容目标在 300ms 内达到可读状态。
- 冷启动单独记录 process-to-first-frame。
- 无法及时展示真实内容时先展示稳定结构，不显示空白页，也不在数据返回后整体更换外壳。

### 4.4 加载、刷新与状态保持

1. 路由转场后的外壳必须稳定；加载完成不得整页更换结构或产生视觉上的二次跳转。
2. 有旧数据时采用 stale-while-revalidate：保留旧内容并后台刷新；刷新失败不得清空已有内容。
3. 首帧只请求构成当前页面所需的数据；辅助区域惰性加载，并复用既有缓存。
4. 分页加载只影响列表尾部，不让整个页面重新进入首屏 Loading；请求必须去重并在末页停止。
5. 返回页面应恢复 Tab、筛选条件、滚动位置和已加载分页；切换 Tab 不得无条件销毁控制器并重新请求首屏。
6. 搜索、筛选和快速切换产生的旧请求必须支持取消、忽略或使用 epoch 隔离。
7. 预取必须有明确数量、距离或生命周期边界，不能无限预取分页、Diff、头像或 Markdown。
8. Markdown、Diff、代码、日志和长列表尽量按可见范围构建；重型解析、语法高亮和转换不得长期阻塞 UI isolate。
9. 图片和头像必须限制解码尺寸，并避免滚动时重复解码。
10. Loading、Empty、Error、Refreshing 和 Loading More 是不同状态；不得用全页 Skeleton 掩盖不必要的状态重建。
11. 优先复用现有 HTTP 缓存、实体缓存、`PaginationController`、请求 epoch 和 Sliver 实现，不再造第二套加载框架。
12. 低内存机器上验证任务串行运行，不并发启动 Flutter、Gradle 或 CMake 构建。

### 4.5 统一治理与特化执行

`ResourceRuntime` 是适合缓存和复用的远程只读资源控制面，不是能自动优化所有数据流的通用加载
算法。接入 Runtime 的新功能必须同时完成治理接入和访问模式设计，不能把“进入 Runtime”直接等同于
“加载已经特化或变快”；长轮询、Stream、本地数据库和命令式副作用仍使用各自专用边界。

1. 先从当前生产入口追踪到正式 Service，再定义当前 UI 真正需要的最小字段投影、资源身份、分页或
   增量语义、mutation 失效和规模上限；Runtime 不负责猜测这些领域合同。
2. 实现前识别访问模式，并优先复用已经存在且有生产回归的执行路径。当前可视为已证明的基础只有直接
   snapshot/source→artifact 资源和 `RuntimeForwardPageSource`；Timeline、Tree、FanOut、Live 等
   是候选分类，不是尚未存在的公共 API。
3. Resource Recipe 只声明 `ResourceSpec`、身份、页键、标签、策略、正式 Loader 和估算权重；访问
   模式执行器负责分页、头部增量、锚点、页窗口、距离式预取或有界扇出等算法；两者都不得复制 Service。
4. Widget 永不直接持有 Lease。简单资源可由显式 Riverpod binding/Notifier 负责构造 Recipe、
   acquire、订阅、presence 和幂等 release；分页等访问模式可由特化执行器/query session 持有 Lease。
   所有权必须单一且可追踪，两类 owner 都不得重实现 generation、Single Flight、调度队列，或另建
   一套资源身份与缓存体系。
5. 新页面允许新增领域投影、Recipe 和薄适配器。如果必须修改 Runtime 核心、通用
   `PaginationController`，或在 Widget 中协调请求，必须暂停并先判断现有执行器是否缺少通用能力。
   当前 Issues/PR 首个分页试点仍在 Widget 中读取 scope 并构造 page source，是已登记的过渡例外，
   不得复制到第二个消费者。
6. 新公共执行器必须对应新的访问模式，至少有第二个明确的潜在消费者，并以领域无关的确定性测试证明
   复用；不得因一个页面的特殊字段或 UI 结构创建专用加载框架。
7. 没有第二个消费者时，页面特有差异保留在领域 Service/Provider 的薄适配器中，不上推到 Runtime
   核心；一旦第二个消费者要求相同算法，再提炼并用两条生产链验证。
8. TTL 必须由数据的新鲜度、一致性和失效合同解释；页大小、预取距离、窗口容量和并发预算必须在
   正确性测试通过后由 Profile/Release 同环境数据调整。请求次数减少只能证明复用或传输变化，不能
   单独证明帧性能或端到端耗时提升。
9. Mutation、上传、评论提交及其他主动写操作继续由正式 Service/Notifier 管理，不绑定页面 Resource
   Lease；成功后通过局部 overlay 或精确标签失效同步相关只读资源。

## 5. Motion 规范

### 5.1 原则与 Token

每次用户可感知的操作都必须获得明确反馈；只有层级、空间、展开关系或模式发生变化时才使用运动动画。

视觉动画的时长、Curve 和位移必须集中在 `lib/common/animations/motion.dart`、`AppMotion` ThemeExtension 或后续等价的单一实现中。页面内不得散落任意视觉 `Duration`、Curve 或位移值；搜索防抖、轮询和通知存活时间等非视觉时序不属于 Motion Token。

| 场景 | 建议基线 | 表现 |
| --- | ---: | --- |
| Hover、按压、焦点 | 80–120ms | 颜色、透明度或轻微状态变化 |
| Loading、Error、Content | 160–200ms | 保持几何结构稳定的淡变 |
| Tab 内容切换 | 160–220ms | Fade；可附加不超过 8 logical px 的位移 |
| 页面进入与返回 | 220–280ms | 符合平台方向的转场 |
| Drawer、Dialog、展开收起 | 200–300ms | 位移、淡变或尺寸变化 |

- 动画必须可中断，不阻止快速连续操作。
- 动画不能触发重复网络请求，不能为动画同时保留多个重型页面。
- Tab 切换必须保持内容状态；页面前进与返回方向语义一致。
- Loading、Error 与 Content 切换尽量保持几何尺寸稳定。
- 不同时堆叠 Fade、Scale、Blur、Slide 等无意义效果。

### 5.2 默认不播放装饰动画

分页追加、实时计数、日志连续刷新、窗口连续缩放、不可见列表项更新、后台缓存刷新、高频进度变化，以及会显著增加布局或 Raster 成本的 Shimmer、Blur 和大范围阴影，默认不播放装饰动画。

### 5.3 Reduced Motion

1. 动画决策必须同时尊重应用内设置、`MediaQuery.disableAnimations` 和平台 Reduced Motion；任一来源要求减少动画时，不得被另一来源覆盖为开启。
2. Reduced Motion 下取消明显位移、缩放、视差和 Shimmer，仅保留即时颜色、选中态和焦点反馈。
3. 关闭动画不得延迟状态更新，也不得改变请求、路由和状态机语义。
4. 新增运动组件必须有 Reduced Motion Widget Test。

## 6. GitHub Dense MD3 排版规范

文字尺寸均指 Flutter logical pixel，不是物理屏幕像素。

| 语义角色 | 字号/行高 | 字重 |
| --- | ---: | ---: |
| 页面标题 | 24/32 | 600–700 |
| Repository 标题 | 20/28 | 600–700 |
| 区块标题 | 16/24 | 600 |
| 文件、Issue、PR 主信息 | 14/20 | 500–600 |
| 普通 UI 正文 | 14/20 | 400 |
| 元数据、辅助信息 | 12/18 | 400 |
| Tab、按钮、紧凑 Label | 13/18 | 600 |
| 代码、SHA、日志 | 13/20 monospace | 400 |

1. 新页面不直接散落裸 `fontSize`，必须通过 `TextTheme`、ThemeExtension 或统一语义组件使用。
2. 不得用缩小文字代替布局优化，不得关闭系统文字缩放。
3. 关键页面必须验证文字缩放 1.0、1.3 和 2.0；允许重排，但不能裁剪重要内容。
4. SHA、路径和日志使用统一等宽字体 Token。
5. 链接、状态、正文和辅助信息不能只靠颜色区分。
6. Android 与 Windows/macOS/Linux 共享语义 Token，可通过集中配置调整密度，不能按平台维护多套排版体系。

建议尺寸边界：

- Linux 文件列表行高目标为 40–44 logical px。
- Repository Tab 目标高度约 40 logical px。
- Desktop AppBar 目标高度约 52 logical px。
- Android 主要触控目标不得小于 48 logical px。
- 桌面可以提高视觉密度，但点击区域不能缩小到难以操作。

## 7. 代码质量与每轮工作合同

每轮修改必须关闭一个明确缺口，不引入新的结构性债务，并为下一阶段保留清晰、可测试的接口。

### 7.1 开始前声明

开始修改前必须写明：

- 本轮目标和明确非目标。
- 正式数据源和现有职责边界。
- 用户可见验收条件。
- 预计修改文件和可能影响的既有行为。
- 停止条件和需要执行的验证。

无法确定正式数据源或现有职责时先调查，不能直接新建替代实现。

### 7.2 实现禁区

- 不为单个页面创建第二套 API、Repository、Provider 或状态模型。
- 不使用演示数据、推测值或硬编码计数伪装完成。
- 不通过硬编码延迟让动画或测试通过。
- 不借功能修改顺手重写整个路由、状态管理或数据库。
- 不大量复制相似 Widget，不散落颜色、字号、圆角、间距、动画值和断点。
- 不引入无责任人、无触发条件、无验证方式的 TODO。
- 不因旧代码难读就删除尚未建立行为测试的功能。
- 不只依赖 Widget Test 宣称视觉或性能完成。

### 7.3 文件职责审查

1. 新增或大幅修改的手写文件超过 400 行必须进行职责审查。
2. 超过 600 行必须按职责拆分，或在结果中写明不拆分的具体理由和后续触发条件。
3. 不为满足行数机械拆成无语义小文件。
4. Widget 同时承担请求协调、状态机、响应式布局和多个独立 Section 时，应按职责拆分；拆分后仍使用同一状态源，不形成重复业务层。

### 7.4 完成标准

涉及 Dart/Flutter 代码的轮次，声明完成前先对“本轮新建/触及文件 + 相关回归”执行定向检查：

```bash
dart format --output=none --set-exit-if-changed <touched Dart paths>
dart analyze --format=machine <touched Dart and test paths>
flutter test --no-pub --concurrency=1 <target test paths>
git diff --check
```

不得在未预览 diff 的情况下对全仓或历史上未整体 format 的旧文件执行批量改写。若全仓基线在当前环境可运行，
再按低内存串行约束补充 `flutter analyze --no-pub` 与 `flutter test --no-pub --concurrency=1`。定向通过只证明本轮
触及路径，全仓基线结果必须单独报告。

并按范围补充：

- 360px、800px、1440px 响应式 Widget Test。
- 文字缩放 1.0、1.3、2.0 测试。
- 页面状态保持、Loading、Empty、Error、Refreshing 和 Pagination 测试。
- Reduced Motion 测试。
- Android 或 Linux Debug Build。
- Profile 模式性能记录。
- 三档宽度截图或 Golden。

`flutter analyze` 不得新增 warning/error；不得删除失败测试换取通过。环境或既有基线导致检查无法运行时，必须记录命令、原因、影响和替代证据。纯文档轮可将 Dart/Flutter 检查标为“不适用”，但不能借此声称运行时已验证。

### 7.5 状态边界与负向验收

状态丢失、重复加载、重复请求、偶发 Provider 异常和“切一下又闪回 Loading”不能只按视觉现象修补。
开始实现前必须建立状态边界表，至少回答：

| 层级 | 必须确认的内容 |
| --- | --- |
| 路由/页面 | 是否创建了新路由实例，返回时是否销毁整页 |
| 页面主 Tab | 子树是否惰性创建、保活或被替换 |
| 页内状态 | Open/Closed/Merged、筛选、搜索文本和排序由谁持有 |
| 查询会话 | 不同 query/type 是否共用或拥有独立会话，缓存容量和淘汰策略是什么 |
| 分页与滚动 | `PaginationController`、游标、已加载 items 和 ScrollController 是否保持 |
| Provider/缓存 | 初始状态由谁构造，何时失效，是否存在 Widget 生命周期写入 |

验收必须把用户操作翻译成事件序列。例如“Open → Closed → Open 不重新加载”至少需要证明：

1. 首次 Open 只产生预期的首页请求。
2. 首次 Closed 产生自己的预期请求和加载状态。
3. 返回 Open 时恢复对应 items、分页和滚动状态。
4. 返回 Open 时请求计数不增加，首屏 Skeleton 不重现。
5. 显式刷新仍只刷新当前会话。
6. 超出有界缓存后的重新请求符合已声明的淘汰策略。

只有结果界面相同不构成证据。空列表、相同测试数据或单张静态截图尤其无法区分“缓存恢复”和“重新请求后
得到相同结果”。相关测试应记录请求参数和次数，并在可行时验证 Controller/会话身份、Loading key 和滚动位置。

业务默认状态必须在 Provider、Notifier 或 Controller 构造阶段建立。Widget 的 `build`、`initState`、
`dispose`、`didUpdateWidget` 与 `didChangeDependencies` 不得写共享 Provider；不得将同一写入简单包进
post-frame 回调作为修复。只有由点击、输入、刷新等明确用户事件触发的状态修改，或有书面职责说明和专项回归的
框架集成例外，才允许从 Widget 发起。

若列表采用 Skeleton，Skeleton 必须反映真实重复行的主要结构，并验证目标断点与 Reduced Motion；一个通用矩形、
一个叶组件或“能看到 Loading”只能证明基础状态存在，不能证明加载体验完成。

用户再次报告已标记完成的问题时，立即将该事项降级为“待复核”。必须重新从生产入口复现、读取当前日志和请求链，
不得以旧测试通过、进度文档已写完成或上下文中的既有结论作为反证。修复后更新原验收映射，明确此前漏测的层级和
新增的负向断言。

### 7.6 收尾闭环审计门禁

本节适用于声明完成、交接、暂存、提交或创建 PR 之前。它检查的是“当前 worktree 真实状态”，不是 agent 的记忆、
旧轮次总结或修改前的测试结果。任一门禁无法满足时，必须降级为“部分完成”、“已登记”或“待验证”，不得继续扩大完成结论。

#### 7.6.1 当前快照与逐文件范围

收尾时至少重新执行：

```bash
git status --short --branch
git diff --stat
git diff --numstat
git diff --check
git ls-files -u
```

若 index 非空，还必须检查 `git diff --cached --stat` 与实际 staged diff。`git diff --stat/--numstat` 不包含 untracked 内容，
因此 `git status` 中每个 `??` 都必须单独追踪。每个变更或未跟踪文件必须归入且只归入以下一类：

| 类别 | 要求 |
| --- | --- |
| 用户授权的功能 | 能映射到本轮精确需求和正式生产入口 |
| 相关回归 | 直接证明该功能的正向结果和禁止事件 |
| 生成或配对文件 | 与 source 同组，可由公开步骤重现，不只有本机产物 |
| 进度/架构/政策文档 | 与当前代码一致，不把未验证内容写成完成或对外承诺 |
| 必要 hygiene | 仅限触及文件不新增 warning/error 或保持 codegen/formatter 所需的最小变化，必须单独说明 |
| 无关或无法解释 | 阻塞完成/暂存/提交；保留用户修改，不用破坏性命令处理 |

对旧文件运行 formatter 前必须先预览可能的 diff。若小功能会引起整文件换行/尾逗号重排，应停止批量改写并收窄为功能 hunk。
不得为减少 diff 而恢复未使用 import/字段、重新引入 analyzer warning，或覆盖用户已有修改。

#### 7.6.2 单一所有权账本

新增、替换或下沉以下任一边界时，必须先做全局定义/调用点搜索，并在结果中提供所有权账本：

- Provider、Notifier、Controller 或业务状态机；
- Timer、polling coordinator、Watcher、Stream/subscription 或 lifecycle observer；
- query session、分页会话、缓存、overlay 或 optimistic mutation；
- Resource Lease、generation、失效标签或背景调度。

| 字段 | 必须回答的问题 |
| --- | --- |
| 资源/动作身份 | 是哪个账号、仓库、query、页、mutation 或长时任务 |
| 正式数据源 | 哪个 Service/GraphQL/REST/本地库负责真实读写 |
| 新 owner | 谁创建、保活、刷新、失效和销毁 |
| 旧 owner | 是否删除、委托给新 owner，或在互斥状态下保留 |
| 生产调用点 | 所有真实 UI/Service 调用者，不只是新测试或示例 |
| 并存条件 | 新旧 owner 能否同时请求、写状态、投递反馈或持有资源 |
| 结束路径 | dispose、invalidate、unregister、账号/scope/query 切换时谁释放 |
| 负向证据 | 哪个测试证明旧 owner 不再启动、两者不同时运行或过期写入被禁止 |

“新路径已有测试”不能证明旧 owner 消失。旧 owner 必须删除、变为对新 owner 的显式委托，或由可证伪状态表保证互斥。
对同一 mutation，所有 UI 消费者必须共享同一个权威写入边界与对账规则。

#### 7.6.3 异步晚返回与销毁矩阵

凡是可能跨越一个 frame、路由、账号或 lifecycle 的 Future/Stream/Timer，都必须根据实际边界覆盖以下矩阵：

| 转换 | 至少需要的证据 |
| --- | --- |
| active → dispose/unregister | 在途晚成功/晚失败不写已销毁状态、不访问已关闭 stream |
| old owner → replacement owner | 旧 generation/identity 结果被丢弃，不覆盖新 owner |
| route/Tab visible → hidden | 停止只有可见期才允许的请求、翻页、动画和反馈 |
| resumed ↔ paused/hidden/detached | 调度所有权唯一，恢复时不立即双重请求 |
| account/scope/query A → B | A 的延迟结果、缓存和反馈不泄漏到 B |

负向断言至少包含适用的：没有 Provider/Controller 写入、没有 event/notification/dispatcher 投递、没有定时重排、没有额外请求、
没有跨账号或跨 query 缓存污染。若底层不能真正取消网络，必须用 generation、identity 或 disposed gate 丢弃晚返回，不得只依赖 `mounted`。

#### 7.6.4 测试日志也是验收输出

退出码为 0 和用例数全绿只是必要条件，不是充分条件。必须审阅完整 stdout/stderr，以下内容默认阻塞完成：

- `Another exception was thrown`、`Failed assertion`、未捕获 Future/Zone 错误或 Flutter 红屏；
- 不在当前测试预期失败路径内的 `[error]`、`[exception]`、Provider failure 或 `Bad state`；
- dispose 后写 stream/Provider/Controller、重复调度、重复请求或未收口的后台任务日志。

若测试主动模拟网络/分页/mutation 失败，预期错误必须能由用例名称、显式断言或注入的 logger/observer 归属到该路径；
无法归属的原始错误日志不得以“测试还是通过了”忽略。结果报告必须说明预期失败日志和非预期日志是否存在。

#### 7.6.5 最后修改后重验

任何会改变运行时、生成接口、测试 fixture 或正式调用链的最后补丁，都使该依赖闭包上之前的验证失效。补丁后必须至少重跑：

1. 本轮新建/触及 Dart 文件的定向 format 检查；
2. 触及生产/测试路径的定向 analyze；
3. 新增失败回归与相关生产入口测试；
4. `git diff --check` 与本节的当前快照。

之后若只更新准确记录检查结果的 Markdown，无需重跑 Flutter；再次修改代码则必须重验。全仓检查中的历史 warning/error 与本轮新增问题
必须分开计数，不得把“0 error 但有 baseline warning”写成“全仓 analyze 清零”。

#### 7.6.6 多功能 worktree 的状态与成组不变量

当 dirty worktree 同时包含多个需求时，必须先按“生产实现 + 相关测试 + 生成/配对文件 + 记录”列出逻辑变更组，并为每组单独标注：

- 已满足；
- 仅建立基础；
- 已登记未处理；
- 待自动验证；
- 待真实账号/平台/Profile 验证。

不得用一组通过的测试扩大为整个 worktree 完成。在暂存/提交设计中，ARB 与 gen_l10n 产物、GraphQL operation 与可重现 codegen 合同、
`part` 父文件与新 part、生产文件与必需测试不得被拆到会使中间状态无法编译或无法复现的不同组。

收尾报告至少提供以下账本：

| 需求/变更组 | 生产入口/所有权 | 正向证据 | 禁止事件证据 | 当前状态 | 未验证项 |
| --- | --- | --- | --- | --- | --- |

空表、只列测试名或仅写“通过”不构成收尾证据。

## 8. 技术债处理

1. 已确认但不在当前范围内的问题登记到 [`technical-debt-register.md`](technical-debt-register.md)。
2. 当前功能轮只处理 P0 和无法绕开的 P1；P2/P3 默认登记后独立处理。
3. 清理旧 UI、替换状态管理或迁移业务模型前，先建立行为测试。
4. 技术债项必须有位置、证据、用户影响、处理路径、风险、前置条件、验证和触发条件；不得只写主观评价。
5. 已解决项目保留记录并写入解决提交与验证，不直接删除。

## 9. 变更与汇报

1. 保留用户已有 worktree 修改，不使用破坏性清理命令。
2. 未经明确授权不 commit、不 push、不创建 PR。
3. 每轮结束必须报告实际修改、实际检查、未运行的检查以及仍未完成的用户可见事项。
4. 进度文档必须与代码一致；发现误报时先纠正状态，再继续实现。
5. 独立审查发现高严重度或会推翻完成结论的问题时，必须先修复或降级为未完成；不得因为此前测试已经通过而忽略新证据。
6. 结束时必须提供“需求—实现—验证”映射，区分已满足、仅建立约束、已登记未处理和待验证。
